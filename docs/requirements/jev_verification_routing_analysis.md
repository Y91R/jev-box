# Аналитика: Jev как слой верификации и маршрутизации для скиллов аналитики и планирования

Ресерч по гипотезе из [jev_verification_routing_research_brief.md](jev_verification_routing_research_brief.md) (далее — «бриф»). Задача — не спроектировать систему с нуля, а сверить бриф с реальным API Jev/TypeSafe и с уже существующими в этом окружении скиллами (`system-analyst`, `analyst-reviewer`, `feature-planner`, `review-plan`) и кодом (`hooks/jev.ts` этого репозитория), и показать, что из брифа подтверждается, что не бьётся с реальностью, и что уже реализовано.

Формат результата — по решению пользователя: только структурированная аналитика, без правок самих скиллов.

## TL;DR

- Гипотеза брифа в целом верна: Jev как дешёвый вероятностный gate перед дорогим ревью (codex/Claude/человек) — рабочий паттерн, прямо описанный в официальной документации TypeSafe (`intent-routing`, `confidence-routing`, `how-to-build-with-system-one`), а не изобретение брифа.
- Главная поправка к брифу: **единица анализа — скорее пункт (требование/шаг), чем документ целиком.** Контракту API формат брифа не противоречит (много вопросов на один `state` — это штатный fan-out), но документ целиком в `state` попадает под «large state full of irrelevant detail», а вопрос «насколько документ специфичен» прячет несколько суждений в одном. Это **гипотеза, проверяемая замером** (§2.1), а не ограничение API.
- Вторая поправка: **internal_consistency между двумя удалёнными требованиями (пример REQ-1/REQ-7/REQ-9 в §6.1) — это как раз то, что Jev делает плохо** («indirection», «large state full of irrelevant detail» в jaggedness-доке). Роль Jev здесь — дёшево тегировать/группировать требования по сущности и статусу, чтобы сузить пары-кандидаты; само сравнение — reasoning-слой (Claude/codex), не Jev.
- Третья поправка: у ответа `noul` **нет** `confidence` (только `choice` и `score` его несут), и `noul` — это вероятность ответа «да», а не мера уверенности модели. Часть сигналов брифа сформулирована как «0–1 сигнал» без уточнения типа вопроса — решение (noul vs score vs choice) принимается по каждому сигналу отдельно, вместе с порогами, и для блокирующих решений тип с confidence предпочтительнее.
- Гардрейл на `tool.check` (§8.2–8.3) — **проработанная гипотеза, а не готовое решение**: форма события подходит, но не закрыты четыре вопроса — монотонность композиции вердиктов (иначе Jev способен ослабить политику пользователя), отправка входных данных каждого вызова инструмента во внешний API, цена и задержка на каждом вызове при общей квоте 20 запросов/с, и калибровка шкалы. До eval-датасета автоматический `allow` от Jev не выдаётся. Тема выходит за рамки действующего СТ `model_choice.md`.
- `hooks/jev.ts` этого репозитория годится как основа **по контракту и форме** (`buildRequest`/`parseResponse`, типизированный `Decision`, коды отказа), но не «как есть»: он жёстко заточен под один Choice-вопрос `model`. Для верификации нужен вариант с картой из нескольких Noul/Score/Choice вопросов сразу (fan-out) — расширение, не перенос. **Решение принято (§7): TypeScript, один клиент на всё; хук выбора модели, гардрейл и будущие верификаторы — потребители общего ядра (§8).**
- Ограничение контекста Jev (32k ток. на `state` + самый длинный вопрос, 64k суммарно) реален и не бесконечен: крупная СТ или план **не влезут одним `state`** — нужна декомпозиция по требованиям/шагам (одно требование/один шаг — один вызов) и/или батчинг нескольких коротких пунктов в один `state`-массив (см. §6).
- Ценность Jev для `analyst-reviewer`/`review-plan` — не замена внешнего ревью codex (оно уже безусловно запускается по скиллу), а **дешёвая приоритизация**: сузить, на какие требования/шаги стоит смотреть внимательнее человеку/codex, и добавить механическую проверку формулировок, которую сейчас в `analyst-reviewer` делает дорогая модель вручную.

## 1. Что реально умеет Jev (проверено по первоисточнику)

Источник: `https://docs.typesafe.ai/*` (сентябрь 2026, `jev-1.13.0`), скачано и прочитано полностью для страниц ниже.

### 1.1 Три примитива, один эндпоинт

`POST https://api.typesafe.ai/v1/systemone` — один запрос: `state` (string | object | array) + карта `questions` (ключ → вопрос) → карта `answers` (тот же ключ). Все вопросы одного запроса считаются **параллельно и независимо** — ответ на один не виден другому. [api.md]

| Тип | Вопрос | Ответ | Несёт `confidence`? |
|---|---|---|---|
| `noul` | yes/no | `noul: 0..1` | **нет** |
| `choice` | выбор из ≤255 опций | `choice`, `probabilities{опция→p}` | да |
| `score` | рубрика из 2–10 уровней | `score` (может быть между уровнями), `probabilities`, `legend` | да |

`confidence` — не отдельная модельная метрика, а статистика, посчитанная из `probabilities` (насколько распределение сконцентрировано на одном варианте). [confidence.md, api.md]

### 1.2 Лимиты и цена (`jev-1.13.0`)

- Контекст: **64k токенов** на `state` + все вопросы суммарно; **32k** — на `state` + самый длинный отдельный вопрос. [models.md]
- Цена: $42 / млрд входных токенов ($0.042 / млн), **выходные токены бесплатны**. Заявление «238x дешевле» из брифа проверено: TypeSafe публикует его на главной с явной базой сравнения — «238x Lower input price than Claude Fable 5.1», и оно сходится ($10.00 ÷ $0.042 = 238.1). Против остальных моделей Claude выигрыш меньше: Opus 5 — 119x, Sonnet 5 — 47.6x, Haiku 4.5 — 23.8x (цены Anthropic на 2026-06-24). То есть выигрыш по входному токену — от ~24x до ~238x в зависимости от того, что именно заменяется; «на порядки» без указания базы сравнения — некорректная формулировка. Цены OpenAI/Codex в этом ресерче не проверялись, поэтому сравнение с ними не приводится.
- Скорость: заявлено ~100 мс на типичный запрос («Fast» в how-to-build). Официальных данных о задержке батча из 40+ вопросов в одном запросе не публиковано — не проверено.
- Rate limits: 250k ток/с, 1200 запросов/мин, **явно помечены как временные и подвижные** («adjusting dynamically» — растут спрос и мощности). Не production-гарантия.
- Модель одна: `jev-1.13.0` (алиасы `jev-latest`/`jev-preview` пока указывают на неё же). Нет отдельных «более сильных» моделей System One на выбор.

### 1.3 Официально рекомендуемая архитектура — совпадает с тезисом брифа

`introduction/coding-agents.md` прямым текстом: Jev — **не** замена LLM-агента (Claude Code/Codex/Cursor), не генерирует текст, не пишет код, не ведёт диалог. Его зона: «route a request to one of a fixed set of destinations, and know how confident that routing is»; «score something on a rubric and branch on the number»; «check whether a statement is true before taking an action». Это ровно роль «probabilistic verifier + router», которую бриф отводит Jev в разделе 3 — **совпадение подтверждено первоисточником, не домысел брифа**.

`concepts/how-to-build-with-system-one.md` формулирует тот же паттерн, что бриф называет "control plane": традиционный код / LLM-агент / **AI-powered software**, где код владеет управлением, а модель отвечает на узкие структурированные вопросы. Разложены практики:

1. Держи детерминированную логику в коде (арифметика, даты, маршрутизация).
2. Декомпозируй `state` — только релевантный контекст, не весь документ.
3. Используй структуру в `state`/вопросах — ссылки на `field[i]` через бэктики вместо склейки строк.
4. **Декомпозируй вопросы** — «probably the most important concept»: узкий атомарный вопрос на одно суждение, а не один широкий вопрос, прячущий несколько.
5. Задавай много вопросов за раз (fan-out) — они считаются параллельно, доп. вопрос почти не влияет на latency.
6. Комбинируй ответы **в коде** (детерминированные правила или взвешенная сумма) — не проси Jev агрегировать самому.
7. Маршрутизируй по `confidence`, а не только по значению ответа.

Пункт 4 и пример «decompose spam detection» / «verify a tool-call trace» в этом же документе — прямой прообраз того, как надо резать `completeness`/`actionability` из брифа: не один Noul «план полон?», а N узких Noul по конкретным пунктам чек-листа (ровно так уже устроен ручной чек-лист в `feature-planner` SKILL.md — он уже декомпозирован на атомарные пункты, просто выполняется моделью, а не Jev).

### 1.4 Паттерн confidence-routing/intent-routing — прямое соответствие §17 брифа

`patterns/intent-routing.md` и `patterns/confidence-routing.md` дают тот же код, что бриф предлагает как «routing policy» (детерминированный `if/elif` по `confidence` и `choice`/`score` в коде, не в модели). Пример из `confidence.md`:

```python
if confidence < 0.5:
    route_to_human(user_message)
elif action.choice == "approve_transfer" and confidence > 0.9:
    confirm_then_execute(...)
```

Совпадает дословно с §17 брифа («Jev выдаёт probabilistic signals; детерминированный orchestration code определяет routing»). Разница только в масштабе стейкхолдеров: у TypeSafe примеры — customer support, у нас — ревью документов/планов, но механизм тот же.

### 1.5 Cookbook «Double-checking citations» — готовый рецепт под §6.2 брифа (Source correctness)

`cookbooks/citation_check.md` решает ровно задачу «соответствует ли артефакт исходной задаче» (source alignment из брифа):

1. Код находит цитату/утверждение в исходнике (по индексу/grep) — не Jev.
2. Один `Choice`-вопрос на пару (утверждение, найденная секция источника): `supports` / `contradicts` / `says_nothing` → 4 вердикта (`verified`/`contradicted`/`unsupported`/`fabricated`, если секция не найдена вовсе).
3. Порог `confidence ≥ 0.8` — вердикт принимается автоматически; ниже — на ручную проверку.

Рецепт закрывает **одно направление проверки из двух** — «не выдумано ли»: по готовому утверждению артефакта ищется опора в источнике. Обратное направление — «не потеряно ли» — им не покрывается в принципе: сигналы `omitted_constraint` и `weakened_requirement` из §6.2 брифа требуют идти от источника к артефакту, а здесь, если утверждение не сформулировано, то и вопроса не возникает. Значит для `source_alignment` нужны два разных этапа, и citation-check — только первый; второй (извлечение ограничений из источника и проверка их присутствия в артефакте) в брифе не спроектирован и остаётся открытым.

В этом, суженном виде рецепт применим к доле работы, которую сейчас в `analyst-reviewer` делает дорогая модель вручную (проверка, что FR не «додумывает» то, чего нет в источнике), и к `converge` (сверка требований с кодом): «claim → cite → verified/contradicted/unsupported».

### 1.6 Три зоны confidence — готовая схема гейтинга, не изобретать заново

`confidence.md` даёт официальный паттерн для любого сигнала с `confidence` (Choice, Score): **высокая уверенность → действовать автоматически; средняя → действовать с оговоркой (подтверждение, ревью, отметка «на усмотрение»); низкая → не действовать, эскалация.** Границы зон — не заводские константы (TypeSafe прямо пишет: «start conservative, test with your own data»), но сама трёхзонная форма — не то, что нужно придумывать: она уже есть в документации и в паттернах `intent-routing`/`confidence-routing`. Для ядра (§9) это готовая форма ответа на любой Choice/Score-вопрос: `act | review | escalate`, а не бинарный «прошло/не прошло».

## 2. Что в брифе не бьётся с реальным API — по каждому пункту

### 2.1 Формат сигналов документа целиком (§9, §20)

Бриф даёт пример:

```json
{ "specificity": 0.98, "internal_consistency": 0.93, "source_alignment": 0.42, ... }
```

как единый JSON-ответ на весь артефакт. **Контракту API это не противоречит**: восемь независимых вопросов по одному `state` — ровно то, что разрешает и рекомендует fan-out (§1.1, §1.3), и ответы придут одним вызовом под теми же ключами. Проблема не в контракте, а в качестве: `state` размером с документ попадает под «large state full of irrelevant detail», а вопрос вида «насколько документ специфичен» — это широкое суждение, прячущее несколько (прямо против «декомпозируй вопросы», §1.3).

Отсюда **гипотеза, а не установленный факт**: сигналы такого рода дают более осмысленный результат, если единица анализа — одно требование или один шаг плана, а не документ. Проверяется сравнением двух прогонов на одном наборе (один вызов на документ против вызова на пункт) — до такого замера обе формы остаются допустимыми. Что бы ни показал замер, из §1.3 (шаг 6) следует одно: агрегировать ответы пунктов в оценку документа (min/max/доля непройденных) обязан код, а не Jev.

### 2.2 `internal_consistency`/противоречия между удалёнными частями документа (§6.1)

Пример брифа (REQ-1 против REQ-7 через REQ-9) требует удержать три отдельных утверждения из разных мест документа и вывести логическое противоречие между ними — это ровно то, что jaggedness-документация называет **indirection** («a question about a property of a property or something that requires multiple hops of reasoning costs accuracy») и предупреждает отдельно про rifle-large state («distractor», context rot). Здесь Jev, по документации авторов, объективно слабее — это System Two задача, которую авторы прямо исключают из зоны применимости («avoid: System Two tasks: more layers of indirections» — итоговый Info-блок jaggedness-доки).

**Вывод:** роль Jev в «logic correctness» — не «найди противоречие», а «дёшево протегируй/сгруппируй»: например, Noul/Choice на каждое требование «к какой сущности/статусу относится» → код группирует по сущности → **только внутри узкой группы** запускается дорогая проверка (Claude/codex) на противоречие. Это соответствует духу §6.1 брифа («Jev может дешёво проверять contradiction likelihood»), но меняет реализацию: Jev фильтрует кандидатов, финальное сравнение — не его работа. Это тот же паттерн, что и `cookbooks/classifying_rag_passages` (Noul отбирает релевантное перед дорогой моделью), просто применённый к парам требований вместо пассажей.

### 2.3 Confidence есть не у всех типов ответа

Часть сигналов брифа сформулирована нейтрально («0–1, чем выше — тем хуже»), без указания типа вопроса. На практике: если сигналу нужен confidence-гейт (низкая уверенность → не действовать автоматически, как того требует §17 брифа), вопрос обязан быть `choice` или `score`, не `noul` — у `noul`-ответа `confidence` не возвращается вовсе. Пример: `product_decision_required` как Noul даст только вероятность «да», без встроенной меры «а насколько Jev сам уверен в этой вероятности» — если такая мера нужна, вопрос переформулируется как Choice `{needs_decision, no_decision}` или как Score.

Также jaggedness прямо предупреждает не сравнивать между собой Noul одного вопроса и Choice того же вопроса, сформулированного как yes/no — они не обязаны совпадать численно (§ «Common-sense structural invariants»). Значит нельзя молча выбирать тип вопроса «как удобнее»: тип фиксируется вместе с порогом и не меняется потом без ре-калибровки.

### 2.4 Числа и подсчёт

Бриф несколько раз опирается на «пересчитать число» как то, что Jev мог бы сигналить (например, косвенно в completeness/точность модели данных). Jaggedness прямо и однозначно: Jev не считает надёжно (символы в слове, вхождения термина, элементы длинного списка) и не делает арифметику/сравнение дат надёжно — это должно остаться в коде. Это уже учтено в `analyst-reviewer`/`system-analyst` (там пересчёт чисел явно поручен модели-ревьюеру через команду, не Jev) — противоречия с текущими скиллами здесь нет, просто нужно не наступить на эти грабли при добавлении новых Jev-сигналов.

### 2.5 Лимит контекста и «весь план/СТ одним запросом»

Реализация «Jev #2 — plan verifier» из §15 брифа подразумевает, по тексту, единый проход по всему implementation plan. Крупный план (комплект `docs/plans/`, как их режет `feature-planner`) легко выходит за 32k/64k токенов, если пытаться отправить его целиком как один `state` с батареей вопросов. Единственный проверенный по документации способ — decomposition per step/per requirement (см. §16 брифа тоже об этом говорит, но не проговаривает лимит явно как жёсткое ограничение).

## 3. `hooks/jev.ts` этого репозитория как основа

Файл `hooks/jev.ts` (обслуживает не связанную с бри­фом задачу — выбор модели Claude на ход) даёт готовый, протестированный контракт, который стоит взять за форму для любого нового Jev-клиента под скиллы:

```ts
export type Decision =
  | { id: string }              // выбор сделан
  | { none: 'low_confidence' }  // confidence ниже порога — не действовать
  | { fail: FailCode }          // network | timeout | http_NNN | bad_response | unknown_model | internal

export function buildRequest(config, text, candidates): JevRequest   // строит тело запроса
export function parseResponse(res, config, candidates): Decision      // разбирает и валидирует ответ
```

Сильные стороны, которые стоит унаследовать буквально:

- **Единый тип `Decision`** с явным различием «нет решения из-за низкой уверенности» и «сбой» (`FailCode`: `network | timeout | http_NNN | bad_response | unknown_model | internal`). Это форма, которую нужно сохранить и обобщить на любой потребитель ядра: недоступность Jev — не блокер пайплайна, а типизированная деградация одного сигнала, которую потребитель решает сам (пропустить, эскалировать, отметить в отчёте).
- **Отдельная обработка провайдера** — `ENDPOINTS: Record<Provider, string>` с двумя каналами (TypeSafe напрямую / OpenRouter `/api/alpha/decisions`) при одинаковом формате запроса/ответа — ровно то разделение, которое brief подразумевает как «провайдер — не решение модели» (см. `CLAUDE.md` этого репозитория).
- **`minConfidence` как явная конфигурация**, а не magic number в коде — поле конфига, а не константа внутри логики. Порог принадлежит вопросу и месту, где вопрос сформулирован, — это буквально следует из «Good vibe coding principles» самого TypeSafe (agent-skill.md): «Put the constants (questions and thresholds) in a single place so they're easy to review».

Ограничения, которые не позволяют перенести файл как есть:

- `buildRequest` строит **ровно один** `Choice`-вопрос с ключом `model`. Под верификацию нужна карта из нескольких вопросов разных типов (`Record<string, NoulQ | ChoiceQ | ScoreQ>`) — обобщение сигнатуры, не косметика.
- `parseResponse` тоже завязан на структуру Choice-ответа (`answer.choice`, `answer.confidence`) — для Noul (`answer.noul`, без confidence) и Score (`answer.score`, `answer.legend`) нужны отдельные ветки разбора.
- Файл — TypeScript-модуль движка Function Hooks (`$`-обёртки через `hostOf`), рассчитан на выполнение **внутри** плагина Claude Code, а не как отдельный CLI. Скиллы вызываются из markdown-инструкции через `Bash`, как самостоятельный процесс — то есть за пределами хука переиспользуется **логика** (форма `Decision`, разбор ответа, коды отказа), а не рантайм-обвязка `ConfigHost`/`hostOf`. По решению пользователя (§8) этот контракт портируется и обобщается на TypeScript в общее ядро — см. §9.

Отдельно: TypeSafe публикует официальный npm/py SDK (`@typesafe-ai/sdk`, `typesafe_sdk`) и готовый агентский скилл (`typesafe-ai/skills` marketplace) — они дают типизацию `ChoiceQuestion`/`ScoreQuestion`/`NoulQuestion` и ретраи из коробки. `hooks/jev.ts` их не использует: `CLAUDE.md` этого репозитория требует ходить в сеть только через `$.http.fetch`, npm-SDK провайдеров не использовать. При переходе к единому TS-ядру (§8) это ограничение действует для той его части, что работает внутри рантайма Function Hooks: там SDK не подходит и типы примитивов пишутся свои — по `api.md`.

Фикстурами они пока **не** зафиксированы: все четыре файла `tests/fixtures/` содержат только Choice-ответ вопроса `model`. Реальных ответов Noul и Score в репозитории нет, как нет и повреждённых/неполных ответов, — то есть разбор этих двух примитивов и обработка битого ответа сегодня не покрыты ничем. Фикстуры на Noul, Score и malformed — предусловие обобщения `parseResponse`, а не следствие.

## 4. Куда это ложится по каждому из четырёх скиллов

Только направление и стыковка с уже описанным в SKILL.md — не готовые правки.

### 4.1 `system-analyst` (сбор СТ)

Из брифовского «Requirements verifier» (§16) в этом окружении сейчас не покрыт Jev-сигналом ни один пункт — проверку формулировок, source alignment, completeness, repository_dependency делает модель-ревьюер вручную. Всё это — кандидаты на новые вопросы (Choice/Score/Noul) в одном фан-аут-вызове на требование, а не на отдельный компонент под каждый сигнал.

### 4.2 `analyst-reviewer` (внешнее ревью СТ через codex + своё)

Codex здесь запускается **безусловно** каждый раз — Jev не заменяет этот шаг и не решает, звать ли codex (в отличие от предложения брифа §10 «invoke Codex только если repository_dependency high» — в `analyst-reviewer` codex всегда читает и код, и соседние документы). Ценность Jev тут — не gate, а **приоритизация находок**: собственное ревью (этап 3 скилла) уже вручную делает то, что расписано в брифе как сигналы (специфичность формулировок, source alignment по цитате — см. §1.5 «citation_check» выше). Дешёвый Jev-проход **до** дорогого ревью мог бы заранее пометить требования с низкой `verifiability`/`source_alignment`, чтобы модель (и codex) целенаправленно смотрели именно туда, а не листали документ построчно — это ускорение и фокусировка внимания, не замена этапов.

### 4.3 `feature-planner` (составление плана)

Собственный чек-лист скилла («Самопроверка перед согласованием») уже декомпозирован ровно так, как рекомендует TypeSafe (атомарные проверяемые пункты: «критерий покраснеет при дефекте», «шаг не тянет за собой незапланированное» и т.д.) — это готовый источник формулировок для будущих Noul/Choice-вопросов по каждому шагу плана, если решение будет распределять этот чек-лист на Jev-сигналы. Раздел брифа «Actionability» (§8) ложится сюда почти построчно.

### 4.4 `review-plan` (внешнее ревью плана через codex)

Симметрично `analyst-reviewer`: codex безусловен, Jev — потенциальная приоритизация «непроверенных утверждений» и «критериев без наблюдаемого дефекта» (пп. 1–2 раздела «На что смотреть в плане» уже описывают ровно то, что могло бы быть Choice/Noul вопросом на каждый шаг) до раунда возражений, а не замена его.

## 5. Ограничения и риски (по документации авторов, не домыслы)

- **Indirection/System Two** — противоречия между удалёнными частями документа, многошаговый вывод — Jev делает это хуже, чем предполагает бриф; логика §6.1 брифа нуждается в пересборке под «Jev фильтрует, Claude/codex сравнивает» (см. §2.2 выше).
- **Context rot при большом `state`** — весь документ целиком одним вызовом снижает точность независимо от лимита токенов; декомпозиция обязательна не только из-за лимита, но и из-за качества.
- **Нет батча по нескольким состояниям в одном HTTP-вызове** — но **есть** возможность засунуть несколько коротких независимых пунктов как элементы одного `state`-массива и адресовать их по индексу в разных вопросах одного вызова (пример подсчёта фруктов в jaggedness-доке, пример «resume vs record» в how-to-build). Для документа из полусотни требований переход на несколько крупных батч-вызовов вместо полусотни мелких — не архитектурная правка, а тонкая настройка, но должна быть проверена на точность (jaggedness предупреждает про «large state» — граница между «полезный батч» и «context rot» эмпирическая, не задокументирована).
- **Rate limits нестабильны** («adjusting dynamically») — не проектировать жёсткую зависимость пайплайна от throughput без ретраев и бэкоффа. Сейчас их **нет**: `classify.ts` делает ровно один запрос, а `FailCode` только называет отказ (различая `http_429` от прочего, что позволяет их добавить, но само механизмом не является). Политику повторов (429/529, `Retry-After`, предел попыток, итоговая деградация) нужно задать отдельно — и, вероятно, отключить или жёстко ограничить её на синхронном пути `tool.check`, где каждая попытка задерживает вызов инструмента.
- **Confidence — не универсальная валюта** — нельзя сравнивать confidence Noul и Choice по одному и тому же логическому вопросу (§2.3); калибровка порогов делается по каждому вопросу отдельно и эмпирически (документация TypeSafe сама пишет: «start conservative, test on your data» — никаких заводских порогов нет).
- **Английский — основной язык обучения**; документы этого проекта на русском. TypeSafe прямо предупреждает не полагаться на Jev для non-English без собственного тестирования и с особым вниманием к confidence. Это не было учтено в брифе вовсе — открытый вопрос калибровки для русскоязычных СТ (см. §7).
- **Одна модель без альтернатив** (`jev-1.13.0`) — нет более сильной System One модели на эскалацию внутри самого TypeSafe; вся эскалация «Jev не справился» уходит сразу в LLM (Claude/codex), ступени между ними нет.

## 7. Принятые решения (пользователь, 2026-09-22)

1. **Решение на TypeScript.** Рассматривался и отдельный скрипт на Python — так проще вызывать из скиллов через `Bash`, но это означало бы второй клиент Jev рядом с уже существующим `hooks/jev.ts`. Выбран TypeScript ради одного клиента на всё решение; цена выбора — необходимость адаптера транспорта для вызова вне рантайма хуков (§8.5).
2. **Контракт `hooks/jev.ts` портируется и обобщается**, а не дублируется: один клиент Jev на всё решение.
3. **Noul (и Score) рефакторятся в общее ядро** — сейчас `jev.ts` умеет только Choice.
4. **Одно стройное решение `jev-box`**: хук выбора модели и гардрейл — потребители одного ядра, а не разные проекты.

Остаётся открытым (не решено, требует эмпирики, а не выбора):

- **Калибровка порогов на русскоязычных документах.** TypeSafe не даёт готовых цифр и прямо предупреждает про non-English; бриф про язык не говорит вовсе. Официальный ориентир — только форма («три зоны», §1.6), не числа.
  **Адресат:** владелец репозитория (он же единственный носитель реальных СТ и планов этого окружения). **Критерий закрытия:** собран датасет из размеченных вручную примеров (минимум — категории §22 брифа), на нём измерены доля ложных пропусков и доля лишних эскалаций, и по результату в код записаны пороги с указанием версии модели и языка (§8.4). До этого пороги в коде — временные, и каждый помечается как некалиброванный.

**Границы действующего СТ.** `docs/requirements/model_choice.md` описывает только выбор модели: ни гардрейла, ни события `tool.check` нет ни в объёме, ни в разделе точек перехвата. Всё, что ниже относится к гардрейлу, — за рамками действующих требований, и перед реализацией требует либо правки этого СТ, либо отдельного документа требований.

## 8. Целевая архитектура: одно ядро, несколько потребителей

Из решений §7 следует форма, которой сейчас нет: `hooks/jev.ts` — не «клиент Jev», а «клиент одного вопроса о выборе модели». Ядро отделяется от потребителей.

```text
              чистое ядро (знает Jev, не знает ни задач, ни транспорта)
        ┌──────────────────────────────────────────────────────┐
        │  типы примитивов: Noul | Choice | Score              │
        │  buildRequest(state, questions) → тело запроса       │
        │  parseAnswers → типизированные ответы + валидация    │
        │  Decision/FailCode: единая деградация                │
        └───────────────┬──────────────────────┬───────────────┘
                        │                      │
              адаптер Hook                адаптер CLI
      ($.http.fetch + $.clock)        (fetch + таймер, свой конфиг)
                        │                      │
        ┌───────────────┴──────┐               │
        │                      │               │
   выбор модели            гардрейл       верификаторы
 (turn.start/step)        (tool.check)      (СТ/план — §4)
        │                      │               │
 candidates → Choice   вход вызова → ?    пункт → набор вопросов
 confidence-гейт       allow|ask|deny     (запускаются из скиллов)
                       ⚠ гипотеза, §8.3
```

### 8.1 Что меняется в существующем коде

| Модуль | Сейчас | Куда идёт |
|---|---|---|
| `hooks/jev.ts` | `buildRequest` строит ровно один Choice-вопрос с ключом `model`; `parseResponse` читает `answers.model.choice`/`confidence` | Ядро: карта вопросов, разбор по типу ответа. Выбор модели становится **одним из** вызовов, а не встроенным смыслом. Типизация — не `Record<string, NoulQuestion \| ChoiceQuestion \| ScoreQuestion>`: такой union не связывает вопрос с формой его ответа и заявленной типизации не даёт. Нужен mapped type, выводящий тип каждого ответа из типа вопроса под тем же ключом, плюс рантайм-проверки (`type` совпал, набор ключей полный, `choice` входит в `criteria`, `probabilities` покрывают опции, диапазоны 0–1) — ответ приходит по сети, и статический тип его не гарантирует |
| `hooks/classify.ts` | `ask()` — транспорт (fetch + гонка с таймаутом + trace), но сигнатура завязана на `candidates` | Транспорт уходит **в адаптер**, а не в ядро (см. 8.5): ядро строит и разбирает, адаптер выполняет. `classify()` остаётся тонкой обёрткой выбора модели |
| `hooks/candidates.ts`, `hooks/turns.ts` | Логика выбора модели | Без изменений — это потребитель, а не ядро |
| `hooks/config.ts` | Конфиг под выбор модели (`models`, `subagentTypes`, `minConfidence`) | Растёт секциями под потребителей; `minConfidence` перестаёт быть глобальным — порог принадлежит вопросу, не решению целиком (см. 8.3) |
| `hooks/register.ts` | Связывает `turn.*`/`agent.spawn` с модулями | Добавляется регистрация гардрейла; `hostOf($)` растёт полями под новые вызовы `$` (ограничение валидатора плагинов из `CLAUDE.md` остаётся) |

### 8.2 Гардрейл на `tool.check`: форма события подходит, стоимость решения — нет

Событие `tool.check` (`docs/requirements/.st-sources/claude-code.d.ts:9728`) по форме даёт то, что нужно:

```ts
type ToolCheckInput  = { tool: string; input: unknown; tool_use_id?: string }
type ToolCheckResult = { decision: 'allow' | 'ask' | 'deny'; reason?: string; rule?: string }
```

`next(e)` резолвится в вердикт движка (правила, режим, собственная проверка инструмента). Хук **решает о вызове, а не меняет его** (переписывает вызов `tool.call`), поэтому гардрейл — это `tool.check`. Событие приходит и как реальный вызов, и как запрос (`tool_use_id` отсутствует на запросе) — на запросе ничего не выполняется, и дважды платить за одну и ту же проверку не нужно.

На этом совпадение формы заканчивается. Прежде чем такой гардрейл писать, нужно закрыть четыре вопроса, ни один из которых не решается выбором события.

**1. Композиция вердиктов обязана быть монотонной.** Типы прямо говорят: «a hook may answer any verdict in either direction; the last word up the chain is the decision». Значит хук, вернувший `allow`, способен **отменить** `ask` или `deny`, выставленный движком, настройками или другим плагином, — то есть ослабить политику безопасности пользователя. Правило: сначала `next(e)`, затем Jev может только ужесточить результат (`allow < ask < deny`) и никогда не ослабляет то, что решено до него.

**2. Входные данные вызова уходят во внешний API.** `input` — это команда `Bash`, содержимое файла при `Write`/`Edit`, пути, аргументы MCP-инструментов; там могут оказаться секреты, ключи и персональные данные. По `models.md` Jev не обучается на запросах клиентов, но zero data retention доступен **только enterprise-аккаунтам** — по умолчанию данные могут удерживаться. Плюс jaggedness прямо предупреждает: `state` не считается враждебным, и содержимое, написанное так, чтобы сдвинуть ответ, его сдвигает, — а здесь `state` целиком приходит из того, что предложила модель. Нужны: список инструментов, которые вообще проверяются, редактирование/нормализация входа, предел размера, и явное правило, что Jev — не граница безопасности, а лишь ещё один советующий голос.

**3. Цена и задержка платятся на каждом вызове инструмента.** Выбор модели — один вызов Jev на ход; гардрейл — по вызову на каждый `tool.check`, и оба потребителя делят одну квоту: 1200 запросов/мин — это 20 запросов/с на аккаунт, а один tool-heavy ход плюс параллельные сабагенты выедают её быстро. Таймаут `timeoutMs ≤ 9000` при лимите хука в 10 с укладывается лишь номинально: бюджета на повтор не остаётся, а каждый вызов инструмента ждёт сеть. Нужны allowlist проверяемых инструментов, отдельный (короткий) таймаут для этого пути, дедупликация «запрос/реальный вызов», ограничение параллелизма и заранее определённое поведение на 429/529/таймаут — и измеримая цель по задержке.

**4. Это за рамками действующего СТ** (см. §7) — `model_choice.md` про гардрейл не знает.

### 8.3 Каким примитивом мерить вызов — открытый вопрос, а не решённый

Напрашивается Noul: `noul` возвращает непрерывную величину 0–1, и две границы на этой шкале дают три зоны `allow`/`ask`/`deny`, без отдельной меры уверенности. Соблазнительно, но **как основание для блокирующего решения этого недостаточно**, и §2.3 этого же документа объясняет почему:

- `noul` — это вероятность ответа «да» на заданный вопрос, а не мера того, насколько модель уверена в самом ответе. Низкий `noul` и «модель не поняла вопрос» с этой шкалы выглядят одинаково, а различать их обязательно: во втором случае автоматический `allow` — это тихий пропуск.
- Шкала не калибрована под пороги: jaggedness показывает, что `P(noul)` и `1 − P(not noul)` не обязаны давать в сумме единицу, и что порог, настроенный на Noul, нельзя переносить на Choice того же по смыслу вопроса.
- Документы и команды здесь русскоязычные, а Jev обучен прежде всего на английском (§5) — то есть неизвестной остаётся и сама калибровка шкалы.

Поэтому для блокирующего гардрейла разумнее `Choice {allow, ask, deny}` с confidence-гейтом (низкая уверенность → `ask`, а не `allow`) либо явно заданный fail-safe для Noul. И до появления eval-датасета (§7) автоматический `allow` от Jev не выдаётся вовсе: разрешение оставляет движок, Jev может только поднять руку.

Что из этого остаётся твёрдым правилом для ядра: **тип вопроса выбирается формой решения, а не привычкой.** Выбор из множества → Choice (+ гейт по confidence). Градация «насколько» → Score. Одно утверждение → Noul. И тип вопроса вместе с его порогами живёт одной константой, потому что порог, снятый на одном типе, к другому неприменим.

### 8.4 Где держать вопросы и пороги

Официальная рекомендация TypeSafe (`agent-skill.md`, «Good vibe coding principles»): вопросы и пороги — в одном месте, чтобы человек мог их отревьюить, не раскапывая код. Сейчас в проекте критерии выбора модели собираются из `description` моделей конфига (`jev.ts`), а порог — `minConfidence` там же в конфиге. Для единого решения это принцип на всё ядро: один модуль вопросов на потребителя (вопрос + тип + пороги рядом), а не россыпь констант по вызовам.

Порог при этом принадлежит не только вопросу. `models.md` прямо советует: откалибровав пороги на конкретной версии, пинить versioned ID вместо подвижного алиаса — `jev-latest` переезжает на новую модель без изменений на нашей стороне, и снятые пороги молча перестают значить то, что значили. Поэтому калибровка хранится с ключом `{версия модели, версия формулировки вопроса, язык, провайдер}`, фактический `response.model` пишется в лог каждого решения, а при смене любой составляющей ключа пороги считаются недействительными до перепроверки.

### 8.5 Ядро и транспорт разводятся — иначе CLI невозможен

Верификаторы СТ/планов (§4.1–4.4) при таком ядре перестают быть «ещё одним скриптом»: тот же клиент, те же типы, та же деградация, другой набор вопросов. Но точка входа у них другая, и это **влияет на форму ядра**, вопреки первоначальной оценке: скиллы работают через `Bash`, отдельным процессом, где никакого `$` не существует, а `CLAUDE.md` требует от кода внутри хуков ходить в сеть только через `$.http.fetch`. Ядро, завязанное на `$`, из CLI не вызывается в принципе.

Отсюда обязательное разделение на три части:

- **чистое ядро** — построение запроса, разбор и валидация ответа, пороги и вердикт; ни сети, ни `$`, ни таймеров, поэтому тестируется без хост-объекта;
- **адаптер Hook** — `$.http.fetch` + `$.clock` для таймаута, конфиг из `~/.config/jev-box/config.json`, коды отказа `FailCode`;
- **адаптер CLI** — обычный `fetch` и таймер, собственный источник конфига и ключа, собственный формат вывода для скилла.

Тогда верификаторы получают вход, не таща за собой рантайм плагина, а хук не знает про CLI. Что именно запускать из скиллов — CLI или хук — решается при реализации верификаторов; разделение нужно в любом случае.
